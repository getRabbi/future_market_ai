# App intelligence: official store reports (D-045)

FUTUREGROW imports each developer account's **official aggregate store reports**. Existing apps need no new release, SDK or code change. One connected account covers every app it publishes, including apps added later.

| Layer | Source | Needs an app update? | What it measures |
|---|---|---|---|
| 1 — store reports (this document) | Google Play bulk reports in the account's Cloud Storage bucket, the Play Developer Reporting API (vitals) and App Store Connect Analytics Reports | No | Installs/uninstalls, installed audience, store listing visitors and acquisitions by country and traffic source (with UTM source/campaign), crashes/ANRs, ratings; Apple downloads, impressions, page views, installations, sessions and crashes |
| 2 — app telemetry (optional, `APP_INSTALL_INTEGRATION.md`) | The app backend's consented Play Install Referrer, first open, activation and session events | Yes | Per-installation attribution, activation and retention |

The two layers are shown side by side and are **never added together**. Layer 2 is not derived from Layer 1.

## What is imported

* **Google Play** (`support.google.com/googleplay/android-developer/answer/6135870`): `stats/installs/installs_<pkg>_<yyyyMM>_<dim>.csv` (country, app_version, and overview when Google publishes one; device/language/os_version/carrier can be enabled), `stats/store_performance/store_performance_<pkg>_<yyyyMM>_{country,traffic_source}.csv`, `stats/crashes/…_{overview,app_version}.csv` and `stats/ratings/…_{overview,country,app_version}.csv`. Files are UTF-16 and are matched by column name, not position. Unknown columns are listed on the file record and are never mapped by guessing. Google posts statistics within 3 to 7 days. A day counts as final 7 days after the object's last update.
* **Play vitals** (Reporting API v1beta1): daily crash and ANR rates (`crashRateMetricSet`, `anrRateMetricSet`), on America/Los_Angeles days (the only time zone the API supports for DAILY data).
* **Apple** (Analytics Reports, *Standard* content level, DAILY instances): App Store Downloads, Discovery and Engagement, Installations and Deletions, App Sessions and App Crashes. A newer instance replaces older rows for the same Date, as Apple specifies. A day is complete after the report's completeness window (2–5 days). Instances are deleted by Apple after 35 days; older history needs a one-time snapshot (one per month, data from 2024-01-01).

Not available, so not shown: `utm_content` in any Play report (Play reports UTM source and UTM campaign only), campaign tokens in Apple Standard reports (Detailed reports only), and the time zone of Play statistics days (not documented by Google).

## Data semantics

* **Unknown is null, never zero.** An empty or "NA" cell, a missing day, a report not yet posted and a permission problem all show as "—" with a coverage status: pending, not yet published, unavailable, permission denied, partial, complete or revised. A reported 0 stays 0.
* Each metric keeps its provider column name, definition, population and aggregation rule (`GET /v1/app-intelligence/definitions`). Daily counts add up over days. Installed-base levels take the latest day. Rates and averages are used only as reported for one day and are never recomputed from breakdown rows. Store listing visitors are daily unique counts, so a range total is not a count of unique people.
* Totals add **the same metric across apps of one platform**, and only when every app has the full period. Android and iOS are never added together.
* Revisions: each (app, report, breakdown, day) has one current source. A newer generation or instance replaces the day's rows, an older one is skipped, and an identical one changes nothing. Re-importing the same version is a no-op. Revised days are counted and audited.
* Campaigns: Play traffic-source rows with a UTM campaign are mapped through the D-041 registry to `post` (a per-post campaign), `program` (a shared campaign such as `eps_daily`) or `unregistered`. This is **attribution reported by Google**, not proof that a post caused installs. Since D-049, campaign sums use only final days of the current report version with admitted evidence (the KPI rule below); provisional days are listed as `excludedDays`, never added. A campaign Google does not list (no visits, or grouped as "Other") is unknown, not zero.
* Growth Brain: per-platform series `app.store.android.user_installs`, `app.store.android.listing_acquisitions` and `app.store.ios.first_time_downloads` (and per-app `…:<app id>`) feed M08 forecasts and Autopilot install goals. Change signals compare the last 28 final days with the 28 before, using quasi-Poisson intervals. They abstain when data is stale (over 12 days) or thin (under 24 days or 10 events per window). A change is an observation, never a causal effect.

### KPI series rules (final completion pass, 2026-11-07)

* **Only final, evidence-backed values become points.** A day's value comes from exactly one report partition, the best breakdown for that metric (a reported total before country rows, then app-version rows; two breakdowns of one day are never added). It becomes a KPI point only when the partition is `complete` (not provisional) and the evidence of its *current* report version is `admitted`. Each point cites that evidence, so a point always comes from the report family of its own metric.
* **All-apps points need every confirmed app.** A per-platform point exists only on days when every confirmed app of that platform has a final value. If one app has no value, that day is unknown, not a smaller total. Confirming an app that has no history therefore removes the earlier all-apps days. The per-app series are unchanged, and ignoring the app again restores the total. Android and iOS series are separate.
* **Revisions and invalidation.** Every sync recomputes the whole 730-day window from the current partitions. A restated day updates its value and evidence in place, and an older version is skipped. A point that loses its support is removed and audited as `analytics.series.points_invalidated`. Support is lost when evidence is rejected or expired, a final value disappears, an app is no longer confirmed or an all-apps day becomes incomplete. Raw reports, observations, evidence and audit records are never deleted. Runs are idempotent and serialized per organization by an advisory lock. The worker reconciles after every account sync, and the Autopilot observe step does so before each cycle.
* **System-owned.** `app.store.*` series cannot be created or appended through `POST /v1/analytics/series` (422); only the store sync writes them.
* **Freshness is per metric.** A signal's freshness and windows come from the newest final, evidence-backed day of *that* metric. Another report family (for example same-day vitals) never makes a metric look fresh. Signals report `latestFinalDay` and `revisedDays`.
* **Goals.** An install goal that names one app, by package/bundle ID, store name or linked brand name, measures that app's own series only (`…:<app id>`), never a total that includes other apps. "All my apps" uses the platform series. If several apps match, the owner chooses before saving. Forecasts are not made from a store series whose newest final value is more than 12 days old. A goal's baseline (and a percentage target from it) needs daily values on at least 80% of the pre-goal window. Otherwise no change versus baseline is stated, and missing days are never counted as zero.
* **Brain context.** The observe step records store trends for the goal's own metric and apps. The Idea Lab and Growth Brain receive only trends with enough final, fresh days, as observational context. Withheld apps are named so no trend is read into missing or provisional data, and no post is credited with installs. Since D-049, an organic Facebook Page goal (whose KPI is not a store series) gets the trends of **its brand's own apps** (Page connection → brand → linked apps), each from its own reports; other apps of the developer account are never included. Install outcomes of individual posts need per-post campaigns (below).

### Per-post store attribution in the Studio (D-049)

* A Studio program with `campaignIdentity: per_post` gives every store link its own `utm_campaign` (`<campaign>_<yymmdd>_<4 hex>`), registered with its post (`report_scope = campaign`). New programs default to it. A program on `shared` (the EPS program, `eps_daily`) keeps one campaign for every post; Google cannot split it, so its results stay at program level. The owner switches with **Content studio › Store link campaigns › Use one campaign per post**; only future links change, and past posts and their registry rows are untouched.
* For each published post with its own campaign, the Studio shows Google's store listing acquisitions and visitors for that campaign over a fixed 14-day window from the post's day, once Google has published final traffic-source reports through the window's end (`awaiting_reports` before that). If the window is reported but Google lists no row for the campaign, the result is `not_listed`: unknown, not zero.
* Learning: these values feed a separate, report-only comparison ("store listing acquisitions by lesson type (Google-reported)") that never changes the calendar. The sample is censored (Google lists a campaign only when it has visits), lesson types follow the weekday, and the comparison needs at least 4 posts per type and 12 in total before it says anything. Program, campaign and platform totals are separate views of the same rows and are never added together.

## Owner setup (once per developer account)

### Google Play — read-only

1. **Service account.** In the Google Cloud console (any project you own), open IAM & Admin › Service accounts › Create service account. No Google Cloud role is needed. Open the account › Keys › Add key › JSON, and download the key file. (If your organization blocks key creation, an admin must allow it for this project.)
2. **Play permission.** In Play Console › Users and permissions › Invite new users, enter the service account's email (`…@….iam.gserviceaccount.com`). Under Account permissions, tick only **View app information and download bulk reports (read-only)**, shown as "View app information" set to Global. Do not grant release, store presence, financial or admin permissions. Google can take up to 24 hours to apply new access.
3. **Optional, for app names and vitals.** In the same Google Cloud project, enable the **Google Play Developer Reporting API**. Without it, reports still import; app names and crash/ANR rates are skipped (never estimated) and the account shows a non-blocking warning with the fix (`warnings` on the account: `PLAY_REPORTING_API_DISABLED`, `PLAY_REPORTING_API_PERMISSION_DENIED` or `PLAY_REPORTING_API_UNAVAILABLE`).
4. **Report bucket.** In Play Console › Download reports › Statistics, choose **Copy Cloud Storage URI** (it looks like `gs://pubsite_prod_rev_…`).
5. **Connect.** In FUTUREGROW, open Autopilot › App intelligence › Developer accounts & apps › Connect a developer account. Choose Google Play, paste the URI and select the JSON key file. You must be an owner or admin signed in with two-factor. Access is checked with read-only calls before anything is saved. The key is encrypted server-side and never shown again.
6. **Apps.** The first sync lists every app found in the bucket and confirms it. An app the key can see only through the API (for example from another developer account) waits for "Report this app". An app already reported by another of your accounts becomes a conflict; resolve it with "Report it from this account". Link apps to brands in the same table.
7. **Verify one real import.** After the first sync (minutes), open All apps. The app's card shows "Reported through <date>", and the detail view lists imported files with status `imported` and coverage `complete` or `partial` for recent months. `GET /v1/app-intelligence/apps/<id>?from=…&to=…` returns the same data. A wrong permission shows `permission_denied` with the fix.

### App Store Connect

1. **Key.** In App Store Connect › Users and Access › Integrations › App Store Connect API, create a team key. **Sales and Reports** is enough to read reports. Asking Apple to start generating Analytics Reports for an app needs an **Admin** key once per app (Apple's rule). Download the `.p8` file (it can be downloaded only once) and note the Issuer ID and Key ID.
2. **Connect.** Choose App Store Connect in the connect form. Either reuse the existing App Store Connect connection or enter the Issuer ID and Key ID and select the `.p8` file.
3. **Request reports.** For each iOS app, click "Request Apple reports" (ongoing; this needs the Admin key). Apple generates the first reports in 1–2 days, then daily.
4. **Verify one real import.** After Apple's first instances appear, the next sync imports them. The app detail shows App Store first-time downloads with "Data through <date>".

Rotating a Google Play key: Developer accounts & apps › the account › **Replace the service account key** (`POST /v1/app-intelligence/accounts/:id/key`, owner/admin with two-factor). The new key is tested read-only against the same report bucket before it is stored. It is then saved encrypted on the same connection. The account, apps, imported files and KPI history keep their identity, and nothing is imported twice. The generic `POST /v1/connections/:id/credentials` refuses Google Play keys because it cannot test them. App Store Connect keys are replaced in Connections. A deleted key shows `auth_failed`, and syncs back off (30 min doubling to 24 h).

Connection errors are specific: `PROVIDER_AUTH_FAILED` (key rejected), `PROVIDER_NOT_FOUND` (bucket), `PROVIDER_PERMISSION_DENIED` (Play permission), `PROVIDER_RATE_LIMITED` (HTTP 429) and `PROVIDER_UNAVAILABLE` (network or Google 5xx). Details carry only the access state, HTTP status and Reporting API state, never key material. A failing optional Reporting API does not block connecting or importing bulk reports. The connection shows `degraded`, and the note says whether the API is disabled in the Cloud project (`SERVICE_DISABLED`) or denied.

## Reporting windows (D-047)

Google posts Play statistics 3 to 7 days late, so a period ending yesterday is never complete. All apps therefore defaults to **Latest 28 reported days** (`GET /v1/app-intelligence/overview?…&window=reported`): the same number of days, ending on the latest day every app in scope has reported. The response states `reportedThrough`, the period actually used and `unpublishedDaysExcluded`. Calendar periods remain available. Totals are unchanged in strictness: a metric is added across apps only when every app reported every day of the period; otherwise the total stays open and `incomplete` names each app and its reported days. Missing days are never filled with zero.

## Operations

* Worker cron `*/10 * * * * store_reporting_tick` queues each due account (`store_account_sync`, one job key per account). Syncs run daily at 06:00–06:40 UTC. A run imports at most 40 files; history continues in follow-up runs 2 minutes apart.
* A lease on the account row serializes syncs. A crashed worker's lease expires after 15 minutes and the next run resumes; each file imports in its own transaction.
* Raw report copies are kept 400 days in object storage (`t/<tenant>/reports/store/…`, `47 4 * * * store_report_retention`). Normalized aggregates, file records and evidence remain. Reports are aggregate; no personal data is imported.
* Routes: `GET/POST /v1/app-intelligence/accounts`, `PATCH /v1/app-intelligence/accounts/:id`, `POST …/accounts/:id/key`, `POST …/accounts/:id/sync` (`{"mode":"incremental"|"backfill"|"discovery"}`), `POST …/accounts/:id/apps`, `POST …/apps/:id/decision`, `POST …/apps/:id/apple-analytics`, `GET …/overview`, `GET …/apps/:id`, `GET …/signals`, `GET …/definitions`.
