# FUTUREGROW AI — Architecture Decision Log

Source documents:

- `01_PRODUCT_MASTER_PLAN.md.md` (Product Master Blueprint v2.0) — **authoritative for features, module scope, compliance, safety and acceptance criteria.**
- `02_FINAL_TECH_STACK.md.md` (Final Validated Tech Stack) — **authoritative for implementation architecture, runtimes, topology and infrastructure limits.**

Precedence rule (D-000): when the two documents disagree, feature/compliance requirements come from the product plan and implementation mechanics come from the tech stack. When they disagree on a *verifiable external fact*, the current primary source wins and the check is recorded here.

Each decision lists: context → decision → consequences. `[U]` marks values the documents leave unspecified; FUTUREGROW never invents them.

---

## D-001 — Orchestration runtime: deterministic Agent Kernel, not LangGraph/Swarm

- **Conflict:** Product plan prefers LangGraph (`OS-LG`) for M07/M23. Tech stack states LangGraph/LangChain/Mastra/CrewAI are *not* part of the v1 critical path and mandates a custom typed Agent Kernel.
- **Decision:** Implement the Agent Kernel in TypeScript (`packages/agent-kernel`) with durable state in PostgreSQL and durable execution via Graphile Worker. Logical roles (Observer → Researcher → Strategist → Creator → Experimenter → Publisher → Optimizer → Verifier) are pipeline stages in one runtime. OpenAI Swarm is excluded (both documents agree).
- **Why this satisfies the product plan:** the plan chose LangGraph for *stateful, durable, human-in-the-loop* execution. Those properties are provided by the persisted execution state machine (D-011), Graphile Worker retries/crash recovery, and the approval workflow. The kernel exposes an `AgentRuntime` interface so LangGraph can be added later without touching the security model.

## D-002 — Model gateway: provider-neutral, in-process, license-gated

- **Conflict:** Product plan lists Qwen3 + vLLM (self-hosted) or a managed frontier model behind a provider-neutral gateway. Tech stack forbids a separate LiteLLM gateway service and has no GPU capacity.
- **Decision:** The gateway lives inside `packages/agent-kernel`. Adapters: Anthropic Messages API (default managed provider) and an OpenAI-compatible adapter (covers self-hosted vLLM/Qwen3 later). Every model must exist in the `model_registry` with `approved_for_production=true` before it can be called; there is **no silent fallback** to an unapproved model. Default registered models are Claude 5 family IDs (`claude-sonnet-5-5`, `claude-haiku-5-5`, `claude-opus-5-5`) seeded as **not approved** — a tenant admin must approve after vendor contract review (product plan `COMMERCIAL` row).
- **Consequence:** With no API key or no approved model, LLM-dependent steps abstain with an explicit `MODEL_UNAVAILABLE` reason. Deterministic engines (policy, maths, verification) keep working.

## D-003 — Google Ads authentication (verified fact conflict)

- **Conflict:** Tech stack says Google Ads requires "OAuth 2.0 plus a developer token". Product plan says developer tokens were sunset on 2026-09-09 and access levels moved to Google Cloud projects.
- **Verification (2026-10-19):** Current reporting of Google's documentation confirms the sunset on 2026-09-09; sending the token is optional and ignored, and access level follows the Cloud project used for OAuth credentials. Latest major API version is v26 (2026-10-15).
- **Decision:** Connector authenticates with OAuth 2.0 only; `developer-token` header is sent only if explicitly configured (legacy compatibility). API version is configuration (`GOOGLE_ADS_API_VERSION`, default `v26`) and is recorded in the capability registry; unsupported/unknown versions are denied.

## D-004 — Media-mix modelling: native Bayesian MMM in the Python analytics job

- **Conflict:** Product plan names Google Meridian (`OS-MER`, TensorFlow Probability/JAX, GPU recommended). Tech stack budgets a light Python job on 0.2–0.5 shared vCPU and 512 MB–1 GB.
- **Decision:** Implement the same model class natively (NumPy/SciPy): geometric adstock + Hill saturation, Bayesian regression sampled by MCMC with ≥4 chains, split-R̂ and ESS diagnostics, priors with provenance, experiment-calibrated ROI priors, posterior contribution/response curves and posterior budget scenarios. Causal language is suppressed when diagnostics fail. A Meridian adapter is an upgrade path documented as compute-blocked (BLOCKERS B-010).
- **Consequence:** Slower MCMC on sandbox CPU (throughput degradation, which the tech stack explicitly permits); statistical rigor is not reduced.

## D-005 — Generative media: Remotion + FFmpeg composition; ComfyUI/generative weights excluded from beta

- **Conflict:** Product plan names ComfyUI (`OS-CUI`, GPL-3.0, GPU) for M14/M15. Tech stack specifies a Remotion + FFmpeg media job and no GPU.
- **Decision:** `jobs/media` renders template compositions (product showcase, UGC-style captioned format, synthetic-persona format with mandatory disclosure overlay) from **owned/licensed uploaded assets** using Remotion and FFmpeg, then records hash, workflow config and rights manifest. Generative image/video/voice models are `[U]` (no vendor or approved weights) → blocked (B-011). Remotion is source-available, not OSI open source; rendering refuses to start until the tenant records its Remotion license eligibility (free-license eligibility or company license), enforced in code.

## D-006 — PostHog and Chatwoot are integrations, not hosted services

- **Conflict:** Product plan lists PostHog (`OS-PH`) and Chatwoot (`OS-CW`) as candidates. Hosting either would exceed the Northflank Sandbox allowance of 2 services / 2 jobs / 1 addon fixed by the tech stack.
- **Decision:** Product events, customer events and conversations are stored natively in PostgreSQL. Optional outbound connectors forward events to PostHog Cloud (capture API) and sync conversations with an external Chatwoot instance when credentials exist (B-007).

## D-007 — Retrieval: full-text search always, vectors when proven

- **Decision (tech stack wins):** Probe `pg_available_extensions` for `vector`. If present, enable pgvector; otherwise store embeddings as `real[]` and compute exact cosine in the application. Because Anthropic offers no embeddings endpoint and no embedding vendor is specified `[U]`, the always-available ranking is PostgreSQL full-text search (`tsvector`/`ts_rank_cd`); vector similarity is blended in only when an approved OpenAI-compatible embeddings endpoint is configured.

## D-008 — Tenant isolation: PostgreSQL RLS + application scoping

- **Decision:** Better Auth `organization` = tenant. Every tenant table carries `tenant_id` and has `ENABLE ROW LEVEL SECURITY` with policy `fg_tenant_isolation … TO fg_tenant USING/WITH CHECK (tenant_id = current_setting('app.tenant_id', true))`. Tenant work runs in a transaction that sets `app.tenant_id` and `SET LOCAL ROLE fg_tenant` (a `NOLOGIN` role without `BYPASSRLS`), so isolation does not depend on remembering a `WHERE` clause. `FORCE` is deliberately not used: the owner role is the explicit *system path* (`withSystem`, used only for cross-tenant queue scans and migrations), and tenant traffic never runs as the owner. Append-only tables additionally get SELECT/INSERT-only grants for `fg_tenant` and mutation-blocking triggers that apply to every role. A test asserts that **every** table with `tenant_id` has RLS and the policy.
- **Risk:** Whether the Northflank managed-PostgreSQL user may `CREATE ROLE` is `[U]`. Startup probes this; if the role cannot exist, the app refuses to start in `production` mode and logs the reason (B-004).

## D-009 — Events: transactional outbox + Graphile Worker; webhook inbox

- **Decision:** Domain state change and its event are written in one transaction to `outbox_events`; a `SECURITY DEFINER` trigger enqueues a Graphile Worker job in the same transaction (atomic, no dual-write). Inbound webhooks are signature-verified on the raw body, then inserted into `webhook_inbox` with a unique `(provider, provider_event_id)` constraint for deduplication. No Redis/Kafka/RabbitMQ (tech stack).

## D-010 — API mutation contract

- **Decision:** Every `POST/PUT/PATCH/DELETE` under `/v1` requires an `Idempotency-Key` header. Keys are stored per tenant with a request hash; a replay returns the stored response; same key with a different body returns `422`. Schemas are Zod, exported as OpenAPI 3.1 at `/v1/openapi.json`.

## D-011 — Execution state machine (product plan, extended)

- **Decision:** States exactly as the product plan: `PROPOSED → EVIDENCE_READY → POLICY_CHECKED → APPROVAL_REQUIRED | APPROVED → PREFLIGHT_VERIFIED → EXECUTING → EXECUTED_UNVERIFIED → VERIFIED | FAILED | ROLLBACK_REQUIRED → ROLLED_BACK | ESCALATED`. Added terminal states required for completeness: `DENIED` (policy), `REJECTED` (human), `CANCELLED` (kill switch / expiry). Transitions are enforced in code **and** by a database trigger; the trigger also refuses `VERIFIED` unless an `execution_proofs` row with verdict `VERIFIED` exists. There is no `SUCCESS` state.

## D-012 — Unspecified business thresholds `[U]`

- **Decision:** No λ values, KPI targets, spend ceilings, frequency caps, quiet hours, calibration gates or approval thresholds are invented. Until a tenant configures its policy:
  - every write action resolves to `REQUIRE_APPROVAL` (never pre-authorized);
  - auto-spend ceiling is 0;
  - Growth Brain utility is reported as `UNSCORED_LAMBDAS_UNCONFIGURED` and the decision requires approval;
  - forecast deployment gates fall back to the baseline model and flag `gate_unconfigured`;
  - lifecycle sends are blocked until frequency caps/quiet hours and sender postal address exist.

## D-013 — Frontend ↔ API authentication across domains

- **Decision:** Recommended deployment uses one registrable domain (`app.<domain>` on Pages, `api.<domain>` on Northflank) so session cookies are same-site (`SameSite=Lax`, `Secure`, `HttpOnly`). Fallback when no custom domain exists: a minimal Cloudflare Pages Function proxies `/api/*` to Northflank so cookies are first-party on `*.pages.dev`. The proxy consumes Workers quota (acceptable for a controlled beta, documented in RUNBOOK).

## D-014 — Package manager and build

- **Decision:** npm workspaces (pnpm is not installed; enabling it via corepack would alter the global Node install). TypeScript (strict), ESM, Node 24 LTS, Vitest, Biome for lint/format, esbuild bundles for container images.

## D-015 — Module-to-code mapping

- **Decision:** The tech stack repo contract lists infrastructure packages only. Module domain services live in `packages/core/src/modules/mNN-*` (one folder per product-plan module, all 24 kept), consumed by `apps/api` (HTTP) and `apps/worker` (jobs). See `docs/ARCHITECTURE.md` for the full map.

## D-016 — Analytics job execution model

- **Decision:** `jobs/analytics` (Python 3.13, NumPy/SciPy/psycopg) runs as a Northflank cron job that drains `analytics_requests` using `FOR UPDATE SKIP LOCKED`, writes results, and emits outbox events. An optional immediate trigger calls the Northflank job-run API when a token is configured. Same model for `jobs/media` and `render_jobs`.

## D-017 — Local verification without Docker

- **Decision:** Tests use real PostgreSQL 17 binaries via `embedded-postgres` and a portable Python 3.13 in `.tools/` (gitignored). No in-memory database substitutes for PostgreSQL semantics (RLS, triggers, `SKIP LOCKED`).

## D-018 — Messaging vendor adapter

- **Decision:** Email delivery adapter targets the Resend REST API because it provides read-after-write status (`GET /emails/{id}`) needed for verification. Vendor choice remains subject to contract/data-processing review (product plan `COMMERCIAL`), tracked as B-008. SMS/WhatsApp/push vendors are `[U]` and their action types are registered as unsupported (deny).

## D-019 — Competitor intelligence collection

- **Decision:** Collector fetches only URLs on a tenant-approved lawful-source allowlist, honours `robots.txt`, rate-limits per host, blocks private/loopback/link-local addresses after DNS resolution (SSRF guard), caps size/time, stores snapshots in object storage with SHA-256, and diffs successive snapshots. REA analysis jobs can be registered only with an authorization record (`legal_approved=true`, ownership/licence attestation, approver identity); execution is blocked because no isolated malware-safe sandbox exists in the Sandbox tier (B-012).

## D-020 — Approvals bind to the exact action

- **Decision:** An approval stores the SHA-256 of the canonical action payload. Any change to the payload invalidates the approval. Approvers need the required role and an MFA-enabled account; the proposer cannot approve their own high-risk action.

## D-021 — Kill switches

- **Decision:** Scopes: `system`, `tenant`, `connector`, `object` (campaign/post/journey), `model`, `agent`. Checked at preflight and immediately before the provider call; engaging a switch cancels queued actions in scope.

## D-022 — Local storage backend

- **Decision:** `packages/storage` implements Cloudflare R2 (S3 API, SigV4) for staging/production and a filesystem backend for local development and tests. `NODE_ENV=production` refuses the filesystem backend.

## D-023 — Autonomous execution requires evidence with a declared freshness SLA

- **Context:** The evidence object has `freshness_status: current|stale|unknown`. Without an SLA, freshness cannot be computed and is `unknown`.
- **Decision:** Agent/system-proposed actions require every cited evidence record to be `admitted`, `current` (derived at read time from `freshness_sla_hours`), permitted for `autonomous_execution`, and not prohibited for it. Evidence with unknown freshness can still support *human* proposals, which then always require approval.
- **Consequence:** Producers of evidence intended to drive automation must declare a freshness SLA; this is enforced by the policy engine, not by convention.

## D-024 — Model routing and refusal fallbacks

- **Default model:** every reasoning purpose (planning, critique, generation, extraction) routes to `claude-opus-5-5`; no automatic downgrade to cheaper models for cost. Adaptive thinking is always on for this model (the `thinking` parameter is omitted); depth is controlled with `output_config.effort` set explicitly per purpose (its default is `medium`).
- **Structured output:** responses are constrained with `output_config.format` (Zod schema via the SDK's `betaZodOutputFormat`) and re-validated with the full FUTUREGROW Zod contract; forced `tool_choice` is not used (rejected by this model).
- **Refusal fallbacks vs. the licence gate:** the vendor recommends server-side `fallbacks: "default"`, but that lets the server pick a model that is not in FUTUREGROW's registry, which the product plan forbids ("never silently switch to an unapproved-licence model"). Decision: send `fallbacks` only as an explicit list of models that are registered **and approved** with purpose `fallback`; when none are approved, no fallback is sent and a refusal makes the step abstain. Every response's served-by model is checked against the approved registry before its output is used.

## D-025 — Lifecycle journeys send as system proposals backed by trigger evidence

- **Context:** Journeys (M20) send without a human in the loop for each message, but system/agent proposals must cite current evidence permitted for autonomous execution (D-023).
- **Decision:** Each enrollment admits pseudonymous first-party evidence (the trigger event) with the journey's declared `evidence_freshness_hours` (1–720, default 168), set by the designer and approved when a different person activates the journey. Every send is a separate `email.send` action proposed by `system:journey:<id>`. Consent, suppression, frequency cap, quiet hours, sender identity (CAN-SPAM) and jurisdiction are evaluated at proposal and re-evaluated at preflight in the same transaction as rendering, immediately before the provider call. Whether sends run unattended depends only on the tenant's `MESSAGING` policy (`pre_authorized_within_limits` with `maxAudienceSize`); otherwise every send waits for approval.
- **Consequence:** Next-best-message selection uses an M10 experiment (`send_experiment` step) so allocation is measurable; there is no opaque model-chosen messaging. DSAR deletion expires the trigger evidence, which stops further sends for that profile.

## D-026 — Parameter resolution happens before any reservation or send

- **Decision:** The M23 gateway calls module resolvers (email rendering, presigned media URLs) inside a savepoint before budget reservation and before the `PREFLIGHT_VERIFIED → EXECUTING` transitions. A resolution error moves `APPROVED → FAILED` with "nothing was sent". During verification a failing resolver falls back to stored params (verification reads provider state by receipt).

## D-027 — Spend reconciliation envelope

- **Decision:** The authorized envelope for a campaign-day is the daily budget in effect at the end of that UTC day, from append-only `ad_budget_history` (sync observations, verified M23 actions, and external changes, which also raise a drift alert). Only days older than `SETTLEMENT_LAG_DAYS = 3` enter the append-only spend ledger; restated settled days raise an alert rather than editing the ledger. A period is a discrepancy when spend on known-budget days exceeds the envelope by more than the tolerance (default 2 %), when a single day exceeds 2× its budget (Google Ads' documented overdelivery cap), or currencies disagree. Spend on days with no known budget makes the result `insufficient_data`, never `ok`.

## D-028 — Retrieval for conversational questions

- **Decision:** Chat (M21) and social replies (M16) query the knowledge base with OR semantics over stemmed terms (`to_tsquery('simple', …)` built from `plainto_tsquery('english', …)`), ranked by `ts_rank_cd`; document search elsewhere keeps AND semantics. Answers are released only if every citation resolves to a retrieved public excerpt, confidence ≥ 0.6, claim/brand lint passes, no commitment (refund, discount, guarantee, delivery date) appears unless the cited excerpt states it, and the customer message shows no injection markers; otherwise the conversation is handed to a human and the AI stops replying in it.

## D-029 — Embedded Postgres clusters are initialised as UTF-8

- **Context:** On Windows, `initdb` defaults to the WIN1252 code page, which rejected non-ASCII text (e.g. "→" in alert messages) that production (UTF-8) accepts.
- **Decision:** Test and dev clusters are created with `--encoding=UTF8 --locale=C` and databases with `encoding 'UTF8' template template0`, matching managed Postgres.

## D-030 — Encrypted logical backups with verification and restore drills

- **Context:** The tech stack assigns backup verification to the analytics job and backups to R2. The Northflank Sandbox Postgres addon's native backup capabilities are tier-dependent `[U]`, and no `pg_dump` binary ships with the runtime images.
- **Decision:** `python -m futuregrow_analytics.backup create` exports every public table from one `REPEATABLE READ, READ ONLY` snapshot via `COPY … (FORMAT csv, HEADER)` (generated columns excluded), gzip + AES-256-GCM per table (key `FG_BACKUP_KEY`, AAD binds archive key and table), into a tar with a plaintext manifest of migration hashes, row counts and member hashes; archive + sidecar manifest go to R2 (SigV4 implemented in Python and cross-checked against the AWS vector and aws4fetch). `verify` checks hashes, decrypts and counts every member; `verify --restore-into` performs a restore drill into an empty database migrated by the same release (user triggers disabled during load, FK order, sequences advanced, migration-owned reference tables skipped), and every run is recorded in the platform-only `backup_runs` table. `backup_verification` is not a tenant analytics request.
- **Consequence:** Restores need the same migrations and an empty target; the backup key must be stored separately from R2 credentials (losing it makes backups unreadable). Managed addon backups, where available, remain the primary point-in-time mechanism; these logical backups are the provider-independent copy.

## D-031 — Invite-only onboarding without outbound email

- **Context:** Disabling Better Auth sign-up entirely made invitations unusable (an invitee could not create the account needed to accept). No platform email provider is configured for the beta (B-008).
- **Decision:** Sign-up stays enabled at the Better Auth level but a `user.create.before` database hook refuses account creation unless `FG_ALLOW_SIGNUP` is set or a pending, unexpired invitation exists for the address (case-insensitive). Owners/admins create invitations in Account & security; the control plane shows the `/invite?id=…` link to share out of band. Accepting requires the invitation id and the matching email; Better Auth's per-IP sign-up throttling stays on.
- **Consequence:** A person who knows a pending invitee's address could pre-register that address but cannot join the organization without the invitation id; the inviter cancels and re-invites. Email verification of invitees is added when an email provider is approved.

## D-032 — Propensity scores are withheld on training/serving feature drift

- **Context:** M11 acceptance requires training/serving feature parity and drift checks. Training features are computed at the label cutoff (now − horizon) and serving features now; the shift between those windows is where silent degradation appears.
- **Decision:** Both use the same feature SQL (parity by construction). Every training run computes a per-feature population stability index (PSI, reference-quantile deciles) between training and serving distributions and stores it in the model metrics. If any feature exceeds 0.25 the model cannot become champion, no scores are written, and an `analytics.propensity_drift` alert is raised.
- **Consequence:** Segments that reference a propensity model only see scores from runs without drift; operators retrain or adjust features rather than consume shifted scores.

## D-033 — Autopilot: durable goal orchestration on the existing kernel, with M23 as the only gate

- **Context:** The 24 modules worked one by one: M07 proposed decisions that a person had to accept before M23 saw them, background jobs automated isolated tasks, and nothing pursued a business objective across modules or cycles. The product plan's M23 is the *Agentic Orchestrator* and Execution Gateway; D-001 already chose PostgreSQL + Graphile Worker for durable, stateful execution instead of LangGraph.
- **Decision:** A goal-driven orchestrator (`packages/core/src/modules/autopilot`) inside M23, built only on PostgreSQL, Graphile Worker and the existing modules — no new infrastructure or dependencies.
  - *State:* `growth_goals` (objective, KPI, target date, authorized channels, advertising budget, limits, cadence, status, memory), `goal_cycles` (one pass, with its plan; a partial unique index allows one running cycle per goal) and `goal_tasks` (checkpointed steps: status, dedup key, attempts, lease, wait deadline, refs, output). RLS applies like every tenant table (migration 0009, additive).
  - *Loop:* observe (M01/M08/M19/M23) → forecast (M08) → research (M04/M05/M18) → ideas (M06) → decide (M07) → content (M13) → submit (M23) → track (M23/M24) → measure (M08) → learn (M06/M10) → next cycle. The planner includes a step only when the goal's channels make it relevant and records why, plus which modules are left out and why. AI is used inside steps (Idea Lab, Growth Brain, creative strategist); it never adds steps, channels or permissions.
  - *Execution:* a minute cron (`autopilot_tick`) queues one `autopilot_advance` job per goal with due work (job key `autopilot:<goal>`); advance runs up to four steps, then yields. Steps hold a 10-minute lease; an expired lease is retried (crash recovery) within three attempts. Waiting steps (analytics job, approvals, verification) are re-checked every five minutes and on events (`action.request.transitioned`, `analytics.request.*`).
  - *Decision → execution:* the Autopilot accepts a goal's decision as `system:autopilot` (`autoAcceptDecision`) and proposes it to M23 with idempotency key `decision:<id>`. M23's policy alone decides: pre-authorized actions run and are verified; everything else waits for a hash-bound, MFA approval; denials become explicit blockers. New rule **R-DECISION** (`fg-policy-1.2.0`): when a decision the Autopilot accepted carries `approvalRequirement.required`, the action needs approval from the category's approvers even if the tenant policy would pre-authorize it (one approval group, so one approver covers both reasons). Decisions accepted by a person behave as before.
  - *EXPERIMENT exception to D-012's utility rule:* an unscored utility no longer forces approval for `experiment.start`, because starting a cheap test is how an unscored idea gets measured; the tenant's EXPERIMENT policy and the "high-risk experiments always need approval" rule still apply.
  - *Goal guardrails:* the Brain's allowlist is filtered to the goal's channel categories and M07 drops actions outside them; a $0 goal cannot include paid ads, and spend beyond the goal budget is refused before M23; social publish decisions get a real M16 post record with the same copy lint and anti-spam guards; daily caps on cycles and model calls, at most N open actions per goal, AI steps spaced 90 s apart (free-tier rate limits), event-triggered replans never sooner than 1 h after the last cycle.
  - *Rollout:* off per organization until an owner/admin turns it on (`tenant_settings.autopilot_enabled`); `FG_AUTOPILOT=off` disables it platform-wide. A tenant kill switch, an agent kill switch on `autopilot`, the system halt, or pausing the goal stop every step.
- **Consequences:** Blocked states are explicit (`needs`: data, evidence, claims, connection, model, budget, configuration, approval) and shown to the owner with the fix; progress is computed only from recorded KPI values and labelled observational. Forecast evidence permits autonomous use only when the tenant configured forecast gates (D-023), so a tenant without gates sees its agent-proposed actions denied — by design, not a bug. The deterministic planner is cheaper and auditable; an AI planner can replace `planCycle` later without touching permissions.

## D-034 — Facebook Page insights become evidence-backed KPI series

- **Context:** A real-Page Autopilot test (2026-10-31, EPS-topik-Bangla) found no way to measure organic Facebook results: the Meta connector read only ad spend and campaigns, and the goal intake mapped "Facebook engagement" to the tenant's first, unrelated KPI series. Graph v26 rejects the older Page metrics (`page_impressions*`, `page_engaged_users`, `page_fans*`).
- **Decision:** `fetchPageInsights` reads the v26 daily metrics `page_post_engagements`, `page_daily_follows_unique`, `page_media_view` and `page_views_total`, one request per metric so a retired metric does not hide the others; a value belongs to the day before its `end_time`, and unfinished days are dropped. M16 `syncPageInsights` admits each fetch as primary metric evidence and upserts the series `kpi.facebook.<metric>` (kind `kpi`, channel `facebook:<page id>`), every point backed by that evidence. The first sync backfills 88 days (inside Meta's 93-day window); metrics with recent values refresh the last 7 days. It runs daily (`page_insights_sync`, 11:25 UTC), on demand (`POST /v1/social/connections/:id/insights/sync`, owner/admin/growth operator), and from the Autopilot observe step when a Facebook KPI is more than two days old (as the Autopilot actor, so its evidence does not trigger another cycle). The goal intake maps engagement and follower goals that mention Facebook, a Page, posts or social to these series, matching the exact key only.
- **Consequences:** No values are zero-filled or invented: when Meta returns nothing, nothing is stored and the sync, the observe step and the forecast blocker say why (missing `read_insights`, or a Page too small for insights). A series belongs to one Page; a second Page connected to the same tenant is refused for that metric instead of being mixed in (per-Page keys are future work). Forecasts still need 33 daily values.

## D-035 — Low-data organic Facebook bootstrap: post counters, brand scope, exploratory drafts

- **Context:** On a small Page (EPS-topik-Bangla, 13 followers) the D-034 insights sync stores nothing: the Page token lacks `read_insights`, and Meta may withhold insights from small Pages anyway. Without 33 daily KPI values there is no forecast, so the Growth Brain (M07) rightly proposes nothing, and the Idea Lab and creative strategist worked from tenant-wide evidence and claims, which in the smoke organization are synthetic and unrelated to the Page.
- **Decision:** (1) `fetchPagePosts` reads the Page's own posts of the last 90 days (≤ 3 requests of 100) with lifetime reactions (`reactions.summary.total_count`), top-level comments (`comments.filter(toplevel).summary.total_count`) and shares (`shares.count`); these need only `pages_read_engagement`. A field Meta leaves out is recorded as `not_returned`, never 0 (Meta omits `shares` when there are none or they are not visible). (2) M16 `collectPagePostSnapshot` stores one primary `snapshot` evidence record per Page and UTC day (`meta://page/<id>/posts@<day>`, with the metric definitions, connection, read time and lineage to the previous snapshot); a second call that day reuses it without a Graph call. Only when the previous snapshot is from the previous UTC day and 12–36 h old is the change between the two reads stored, as points of the separate signal series `signal.facebook.posts.{reactions,comments,shares}_change` (channel `facebook:<page id>`); a post counts only when both reads returned the counter or it was created after the first read. Nothing is backfilled and the Page-insights KPI keys are never written. It runs in the daily `page_insights_sync` job, on demand (`POST /v1/social/connections/:id/posts/snapshot`) and from the Autopilot observe step. (3) `syncPageProfile` reads the Page profile at most weekly into evidence and keeps the Page's product fact (`kg_entities` kind `product`, key `facebook-page:<id>`) with stable fields only, so follower counts do not supersede it and expire linked claims. (4) `pageBrandScope`: a claim belongs to a Page when it is linked to that fact or cites the Page's own evidence; nothing else is used for that Page. (5) Bootstrap: an `organic_social` goal with a connected Page and fewer than 33 KPI values runs observe (profile + snapshot), research (deterministic posting observations), Idea Lab on the Page's evidence only (ideas labelled exploratory: `impactModel.basis = exploratory`, `forecastValidated: false`, route at most `discovery_test`), and content: one model call (`creative.organic_post_drafts` 1.0.0) drafts an `[Exploratory]` M13 brief and ≤ 3 Facebook posts in the market's language (BD → Bangla) stating only the Page's approved claims. Each post is copy-linted (Bangla claim triggers added; `।` ends a sentence) and saved as `social_posts.status = 'draft'` with review metadata; drafts that cite other claims or fail lint are dropped. The forecast step still blocks on data and M07 still requires a forecast, so no decision, action, spend or publication follows. A person schedules a draft (`POST /v1/social/drafts/:id/schedule`; lint and anti-spam again, the person becomes the author, then M23 policy and approval) or discards it; the Autopilot inbox lists drafts with their claims.
- **Consequences:** Small Pages get truthful, reviewable work without pretending to have forecasts. Post counters are snapshots of lifetime totals; day-over-day changes appear from the second consecutive daily snapshot. Drafts stay blocked until someone other than the claim's author approves claims about the Page's product. Bangla lint is keyword-based and catches common superlatives, guarantees, percentages and comparisons, not every possible claim; human review remains required. Multiple Pages per tenant: drafts target the first connected Page and use that Page's scope.

## D-036 — Autonomous organic publishing: the Autopilot's drafts reach M23 by themselves

- **Context:** D-035 left every exploratory Facebook draft waiting for a person to schedule it, so the owner had to operate the product daily, contrary to D-033 (M23 policy is the only gate). Two more gaps stopped an unattended loop: the Page post snapshots and profiles the Autopilot reads itself were not permitted for autonomous execution, so M23 would deny any AI proposal citing them (D-023); and an idea whose drafts existed was never marked tried, so later cycles stalled on it.
- **Decision:** (1) In bootstrap mode the submit step hands one of the cycle's drafts to M23 (`submitPostDraft`) as the agent `autopilot` (with the drafting prompt's version), idempotency key `autopilot-post:<post id>`, the goal's market as geography, and the evidence it acted on: the idea's evidence plus the Page's current post snapshot. Copy lint and the anti-spam guards run again first. Claims stated in the post are checked by R-CLAIMS (approved, unexpired, not regulated), so earlier claim approvals are reused and no post needs its own fact approval. M23 policy alone decides: `PUBLIC_PUBLISHING: pre_authorized_within_limits` with a legal-approved market executes the post and verifies it by read-back; otherwise it waits at APPROVAL_REQUIRED for the usual hash-bound MFA approval; a denial becomes an explicit blocker and the post returns to the drafts with the reason, so a person can still schedule it, and the Autopilot never offers it again. (2) Limits: only goals that auto-submit (suggest-only goals keep D-035's review-only behaviour), at most `maxOpenActions` open actions, and the new goal limit `maxPostsPerDay` (default 1, rolling 24 h by the Autopilot's clock; denied, rejected and cancelled offers do not count), plus the existing 15-minute spacing and 7-day duplicate-caption guards. (3) Page post snapshots and Page profiles — the tenant's own account data read through its authorized connection — are admitted with `autonomous_execution` permitted, like M17's campaign and spend syncs; owner-supplied evidence keeps the uses its owner declared. When a goal auto-submits, bootstrap ideas cite only Page-scope evidence permitted for autonomous execution (when there is any), so an idea the Autopilot will act on does not rest on evidence the owner kept from automation. (4) An idea whose post reached M23 is marked tried with the action's outcome, so the next cycle works on a new idea; the measure step reports each verified post's lifetime counters from the Page's newest daily snapshot (observed values only; null where Meta returns nothing) next to the KPI measurement. `goalActions` and the inbox link post actions to their goal through the post's review metadata. (5) Proposing as an agent means an agent kill switch on `autopilot` also stops queued publications at preflight; connector, tenant and system switches deny as before.
- **Consequences:** Under an explicit pre-authorization an eligible post goes from AI draft to verified publication with no person involved (worker test against a fake Graph API). Exploratory posts are not forecast-validated and stay labelled so; like D-033's EXPERIMENT exception, a $0 organic post is the cheap test that measures an unscored idea. Owners who want to see every post keep `PUBLIC_PUBLISHING` at `approval_required` (the default for an unconfigured policy) or make the goal suggest-only. A policy change never approves an action that is already waiting. No migration: limits are JSON and existing goals get the default. Snapshots stored before this change lack the new permitted use; the next daily snapshot has it.

## D-037 — Jurisdiction rule packs: scoped to a review domain, drafted first, approved with MFA-bound legal sign-off

- **Context:** A Bangladesh readiness review (2026-11-01) found three gaps in D-012's jurisdiction gate. M23 treated a jurisdiction as legal-approved when any approved pack existed for it, so a pack reviewed for one activity (for example organic posts) also cleared advertising spend, messaging and data export there. `POST /v1/platform/jurisdiction-rules` checked only the platform-admin flag, not a two-factor session. And one request both submitted a pack and approved it (`approve: true`), so a technical API call stood in for legal review.
- **Decision:** (1) A closed set of review domains (`JURISDICTION_DOMAINS` in contracts) maps every action type the jurisdiction rule applies to onto exactly one domain: `organic_social` (Page/media/video publishing), `social_engagement` (comment replies), `advertising`, `messaging`, `pricing_promotions`, `store_listing`, `data_export`. M23's `approvedJurisdictions` fact is computed per action type: a jurisdiction counts only when the tenant lists it and a legal-approved pack exists for that action type's domain; an action type outside every domain is never covered. The policy engine is unchanged. (2) Submitting a pack only records a draft version (strict schema: jurisdiction code, known domain, rules, at least one http(s) source URL; an `approve` field is refused), audited as `governance.jurisdiction_rules.drafted`. (3) `POST /v1/platform/jurisdiction-rules/:id/approve` requires a platform administrator with a verified MFA session and an MFA-enabled account, the draft's content hash (canonical JSON of jurisdiction, domain, version, rules and sources, bound like an action hash) and a sign-off (`reviewerName`, `reviewerRole`, `reviewedAt` not in the future, `statement`, `documentRef`). The approval stores the sign-off, the approved hash, approver and time on the row, is audited as `governance.jurisdiction_rules.approved` in the acting organization's chain in the same transaction (`enterTenant`), and cannot be repeated or edited; a change needs a new version. `GET /v1/platform/jurisdiction-rules` lists versions with status and content hash. (4) Migration 0010 adds `created_by`, `sign_off`, `rules_hash`, a domain check and `jurisdiction_rules_approval_chk` (an approved row needs approver, time, sign-off, hash and sources), after turning any earlier approval without sign-off back into a draft (production had none). (5) The Autopilot's market check and Business setup readiness report markets per domain (`marketScopes`), using the goal's channels (`CHANNEL_JURISDICTION_DOMAINS`).
- **Consequences:** A BD `organic_social` pack lets pre-authorized organic Facebook, Instagram, TikTok and YouTube posts targeting BD run without the legal approval group, and nothing else: replies, ads, discounts, store listings, messages and data exports in BD still wait for legal approval until their own domain is reviewed. No action type represents recruitment or migration services, so no pack can authorize them. Tenant autonomy policies, action approvals, kill switches and tenant isolation are unchanged. The pack's `rules` content remains documentation for reviewers; enforcement of its prohibitions comes from approved claims, copy lint and tenant brand rules.

## D-038 — Copy lint: claimed scope and outcome promises must match a cited claim

- **Context:** The first real Autopilot cycle on a Bangla Facebook Page (2026-11-01) drafted "অ্যাপের সব লেসন ও অনুশীলন অফলাইনে ব্যবহার করা যায়" ("all lessons and practice work offline") against an approved claim that covers only the lessons available offline. Copy lint passed it: no claim-trigger phrase matched, and `covered()` accepts a sentence that repeats most of a claim's words even when it drops a qualifier and adds "all". The brief's call to action also used "শিখা" (flame) for "শেখা" (learning).
- **Decision:** `lintCopy` blocks a sentence that uses a scope-widening word (all, every, always, unlimited, fully, anytime; সব, সকল, সমস্ত, প্রতিটি, সম্পূর্ণ, পুরো, সবসময় …) or an outcome promise (fluent, master, "in 30 days", you will pass; পাস করবেন, নিশ্চিতভাবে, সাবলীল, সহজেই, দ্রুত শিখুন …) unless a cited approved claim contains the same word (`OVERSTATED_SCOPE`, `UNSUPPORTED_PROMISE`). Words are matched whole on NFC text with letter-and-mark boundaries, so "সবচেয়ে" is not "সব". Organic drafts in Bangla get deterministic spelling fixes before lint (`fixBanglaSpelling`: শিখা/শিখার/শিখায় → শেখা/শেখার/শেখায়), and the drafting prompt (`creative.organic_post_drafts` 1.1.0) asks for each claim's exact scope and standard spelling.
- **Consequences:** Every lintCopy caller (scheduled posts, Autopilot drafts and submissions, replies, briefs, offers, templates) applies the check; drafts that overstate are dropped with the reason. A claim that itself says "all" still permits "all". The check is lexical: it catches widened scope and stated promises, not every paraphrase, so claims review and the approval gate remain the main controls.

## D-039 — Ordinary organic Facebook Page posts need no jurisdiction rule pack

- **Context:** After D-037 every public-facing action in a market without a legal-approved rule pack waited for a legal-group approval. For the Autopilot's daily educational Page posts (Bangla posts for BD) that meant a recurring legal prompt for content that already passes approved claims, copy lint and the tenant's brand rules, and a pending post (f27b8d3a) that no automation could move: the database only lets a person's hash-bound approval take an action from APPROVAL_REQUIRED to APPROVED.
- **Decision:** Policy `fg-policy-1.3.0`: `social.facebook.publish_post` skips the jurisdiction rule (recorded as `ORGANIC_EDUCATIONAL_POST`) when the owner pre-authorized PUBLIC_PUBLISHING, the post cites only approved, unexpired, unregulated claims, M23's own copy lint of the exact message passed (new `organicPost` fact), it has no link, spend, paid partnership, synthetic persona or protected population, it names a market, and it matches none of the built-in restricted topics (recruitment/jobs, migration/visas, government or official affiliation, guaranteed outcomes; English and Bangla, NFC-normalized). An Autopilot post that fails the topic screen or copy lint is denied (`ORGANIC_POST_RESTRICTED`) so it is redrafted rather than queued for approval; a person's post keeps the old legal path. When the policy changes while an Autopilot post waits for approval and would now be pre-authorized, the track step cancels the waiting action (it can never publish) and proposes the same payload as a new action, which the post and the cycle follow (`resubmitWaitingPost`).
- **Consequences:** Paid advertising, other publishing channels, outreach/messaging, data export, regulated claims, kill switches, evidence rules, rate limits, the daily post limit and the duplicate-caption guard are unchanged, as are the approval trigger and audit log. The topic screen is lexical; approved claims and the tenant's brand rules remain the main content controls. No migration.

## D-040 — Content studio: verified lessons, branded cards and photo posts

- **Context:** The Autopilot published one model-drafted text post a day about the EPS Topik Bangla app. Those posts described the product instead of teaching, a model cannot be trusted to write Korean or Bangla correctly, and no image left the system. Group publishing is not available to apps (Meta removed the Groups API with Graph v19.0, 2024), and the free tier has no approved image-generation model or stock-photo key.
- **Decision:** A content studio (`packages/core/src/modules/studio`, `@futuregrow/visuals`, migration 0011) turns a Page's curriculum program into a seven-day calendar and one visual post a day, with no model call. Korean and Bangla come from a hand-checked lesson bank (`eps-topik-bn`: 50 words, 24 Hangul letters, 15 grammar points, 10 common mistakes, 8 dialogues, 8 notices, plus review quizzes and weekly challenges); captions come from educator-written phrase banks. Cards are typeset with HarfBuzz (shaped glyph outlines, Noto Sans KR/Bengali, SIL OFL) and rasterized with resvg; every card passes QA (glyph coverage, overflow, safe area, overlaps, ≥30 px type, WCAG contrast, size) and a near-duplicate check, then becomes an M14 asset with provenance, template/source/font rights and copy lint of its text. `social.facebook.publish_post` carries up to 10 images with their content hashes; the Meta executor uploads the exact bytes (multipart `/photos`, or unpublished photos + `attached_media`) and verification reads back message, publish state and photo count. Policy `fg-policy-1.4.0`: M23 verifies a post's Korean against the curriculum unit it cites; a lesson citing no claim is pre-authorized only when that check passes and it does not mention the product; any link (field or text) must be the Page product's own Play listing read from admitted evidence; a curriculum mismatch from the Autopilot is denied. The planner rotates lesson types by weekday, reviews taught words, caps app mentions (2) and store links (1) per rolling week (one mention and no link in the first week), adds an app-capability post every 14 days, and moves a slot between lesson types only when both have ≥3 measured posts, ≥8 in total and a ±25% difference. Engagement = reactions + 2·comments + 3·shares from the Page's daily read-back, taken 1–7 days after publication. The community workspace stores groups and their posting permission, ranks them by topic (groups about jobs, visas or agencies get 0), prepares lesson share kits (no app mention or link) or an admin request, and records shares the owner confirms; nothing is posted to groups.
- **Consequences:** No AI calls and no paid service for daily content. AI-generated and stock images are not used: no approved free provider exists, and the asset pipeline would require a model licence or rights record for them. Owner-uploaded, rights-recorded images remain possible through M14. Installs are not attributed: links carry a Play referrer (UTM) for Play Console, which is not imported. Reach and link clicks need `read_insights`. Existing text-post and approval paths are unchanged; the pack version is part of each post's curriculum reference, so a post composed from an older bank version is not pre-authorized after the bank changes.

## D-041 — Brands and an explicit campaign identity registry

- **Context:** A tenant could market several products, but nothing modelled a brand: a Studio program was tied to one Facebook Page and conversion reports grouped installs by free-text `utm_campaign`/`utm_content`, so an install could not be traced to the program, post or channel account that produced it. The Studio's `utm_content` (`<kind>-<serial>`) reused a serial after a failed submission, so two posts could share one identity.
- **Decision:** Migration 0014 (additive) adds `brands` (validated profile: voice, palette refused below WCAG AA 4.5:1, bundled OFL fonts only, ISO countries, BCP 47 languages, objectives, store/web destinations, limits with paid budget 0 by default), `brand_channels` and `brand_apps` (each channel account and each store app belongs to exactly one brand; the app id is parsed from the listing URL), `campaign_links` and nullable `studio_programs.brand_id`. A program joins a brand only through its channel account. The Studio's store links use `<kind>-<yyyymmdd>` (unique per program by `content_plan_day_uq`), campaign names are unique per tenant, and every drafted link is registered with its brand, program, plan item, post and channel — or refused (program without brand, app not that brand's, identity already registered to other content) and left unmapped. M19 campaign reports attach the registered identity and can be scoped to a brand; unregistered rows stay `unregistered`.
- **Consequences:** Existing programs (EPS TOPIK Bangla) keep working with `brand_id` null until an owner links them; their earlier links (`<kind>-<serial>`) stay unmapped. Identity is attribution of a supplied campaign, never a causal claim. Optimistic, versioned brand edits. Another tenant's ids read as "not found" (RLS).

## D-042 — Platform readiness, per-platform formats, LinkedIn and X connectors

- **Context:** The product targets Facebook, Instagram, X, Reddit, YouTube, TikTok and LinkedIn, but the UI had no honest view of what each could do, captions were silently clipped per platform, and LinkedIn/X had no connector. Official terms checked 2026-11-04: X API is pay-per-use with no free posting tier ($0.015 per post, $0.20 with a URL); LinkedIn organization posting needs the gated Community Management API (`w_organization_social` and a page role); Reddit requires explicit API approval and a contract for commercial use.
- **Decision:** `platformReadiness` reports one status per platform with reasons: `live_verified` only with a read-back-verified post in the last 14 days, otherwise `ready`, `needs_connection`, `connection_unhealthy`, `missing_permissions`, `awaiting_approval`, `needs_video`, `disabled` or `owner_assisted`. `checkCaption` applies each platform's limits (X weighted length per twitter-text v3, Instagram hashtags, non-clickable links, video-only platforms) and scheduling refuses copy that does not fit. New connectors: LinkedIn Posts API (hash-bound image upload, little-format escaping, read-back, delete rollback, health requires a posting role) and X API v2 (hash-bound media, t.co-tolerant read-back, delete rollback). `social.x.publish_post` ships `supported: false` (B-019), so M23 always denies it. Reddit is not a connectable provider: share kits stay owner-assisted. Migration 0015 widens provider/platform checks only. Incoming comments get an explainable spam/duplicate verdict; likely spam and duplicates get no model call or draft.
- **Consequences:** Instagram, YouTube, TikTok and LinkedIn publishing remain fixture-tested until real connections and platform approvals exist; YouTube/TikTok also need video, which the Studio does not produce. Enabling X is an owner spending decision plus a capability-registry change.

## D-043 — Uncertainty-aware Studio learning

- **Context:** The calendar moved a slot on raw mean "lift" after three posts per lesson type — small samples, no uncertainty, and lesson types are confounded with weekday (quiz is always Tuesday).
- **Decision:** `compareArms` fits Gamma–Poisson posteriors of engagement per post, widened by the pooled overdispersion (quasi-Poisson), compared by deterministic Monte Carlo. It needs ≥4 complete, frozen observations per group and ≥12 in total; one slot moves only when one lesson type beats another with ≥95% posterior probability. Unknown outcomes are ignored, not zeroed. Credible intervals and P(best) are reported for lesson type, palette, objective and hook; only lesson type acts.
- **Consequences:** Small or noisy histories keep exploring. Notes state that results are associations, not causal effects. Conversion outcomes join the learning only once registered identities and reconciled windows exist (none live yet).

## D-044 — Provider-neutral creative media

- **Context:** The Studio renders branded cards only; the owner wants stock photos, AI illustrations and verified screenshots where rights allow, without rebuilding the Studio, and without paid or unlicensed sources being switched on implicitly (B-011, free-tier rule).
- **Decision:** A `MediaProvider` registry (template cards, verified uploaded assets, licensed stock library, image-generation model) with explicit enablement: stock needs a configured vendor and a production-approved `stock_media` licence with commercial use; AI images need a production-approved `image_generation` model with commercial use and no training on customer data; uploaded images need stored M14 publish eligibility. `mediaQa` gates every candidate (type, content hash, minimum size and exact aspect for 4:5/1:1/1.91:1/9:16, commercial licence, provenance, AI disclosure). GET `/v1/media/providers`.
- **Consequences:** Today only the template renderer is enabled; no vendor adapter is shipped until a vendor and its licence are chosen. Branded templates remain the fallback.
